# معماری سامانه — دستیار حقوقی و اداری پرستاران

> **آخرین به‌روزرسانی:** ۱۴۰۵/۰۷/۱۲ (۲۰۲۶-۱۰-۰۳)
> **وضعیت سند:** معتبر — بخش «پیاده‌سازی‌شده» با اجرای واقعی روی کانتینر تأیید شده است.
> **قاعدهٔ خواندن:** بخش ۲ وضعیت *اکنون* است؛ بخش ۵ معماری *هدف* است و هنوز ساخته نشده. این دو را با هم اشتباه نگیرید.

---

## ۱. خلاصهٔ یک‌خطی

یک وب‌اپ Next.js (App Router) با رابط فارسی راست‌به‌چپ که پرسش پرستار را به یک مدل زبانی از طریق UniRouter می‌فرستد، پاسخ را در قالب چهاربخشی نمایش می‌دهد و تاریخچهٔ گفتگو را در مرورگر کاربر نگه می‌دارد.

---

## ۲. معماری پیاده‌سازی‌شده (اکنون)

```
┌──────────────────────────────────────────────────────────────┐
│                    مرورگر کاربر (Client)                     │
│                                                              │
│  app/page.tsx  ── داشبورد بنتو (۱۲ ستونه)                    │
│  app/chat      ── گفتگوی تخصصی                               │
│  app/archive   ── آرشیو گفتگوها                              │
│  + ۹ صفحهٔ دیگر (payroll, leave, transfer, plan, case, ...)  │
│                                                              │
│  lib/chat-store.ts ── localStorage (تاریخچهٔ گفتگو)          │

│  components/ThemeToggle.tsx ── تم روشن/تیره + localStorage   │
└───────────────────────────┬──────────────────────────────────┘
                            │  POST /api/chat  { message }
                            │  (فقط متن پرسش — هیچ داده هویتی)

│              لایهٔ سرور (Next.js Route Handler)               │
│                                                              │
│  app/api/chat/route.ts                                       │
│    ├─ اعتبارسنجی ورودی (message باید رشتهٔ غیرخالی باشد)      │
│    ├─ تزریق SYSTEM_PROMPT (قالب ۴ بخشی + برچسب نمونه)         │
│    ├─ fetch → UniRouter /chat/completions                    │
│    └─ لاگ ساختاریافته (model, contentLength, usage)          │
│                                                              │
│  app/api/health/route.ts ── healthcheck کانتینر              │
└───────────────────────────┬──────────────────────────────────┘
                            │  HTTPS + Bearer token
┌───────────────────────────▼──────────────────────────────────┐
│                  UniRouter (سرویس بیرونی)                     │
│  https://api.unorouter.com/v1/chat/completions               │
│  مدل: gemini-3.6-flash:free                                  │
└──────────────────────────────────────────────────────────────┘
```

**نکتهٔ کلیدی:** هیچ پایگاه داده‌ای وجود ندارد. کلید UniRouter فقط در `.env.local` سمت سرور است و هرگز به مرورگر نمی‌رسد. تاریخچهٔ گفتگو صرفاً در `localStorage` مرورگر کاربر ذخیره می‌شود.

## ۴. جریان داده (پیاده‌شده)

1. **ورود کاربر** → داشبورد `/` بدون ثبت‌نام؛ تم از `localStorage` بازیابی می‌شود.
2. **طرح پرسش** → `HeroSection` متن را می‌گیرد و به `/chat?q=...` هدایت می‌کند.
3. **گفتگو** → `app/chat/page.tsx` پیام را به `POST /api/chat` می‌فرستد.
4. **سرور** → اعتبارسنجی، تزریق system prompt، فراخوانی UniRouter، لاگ.
5. **پاسخ** → قالب چهاربخشی (فهمیدم / لازم است / مبنا / قدم‌ها) با برچسب «نمونه».
6. **ماندگاری** → پیام‌ها در `lib/chat-store.ts` روی `localStorage` ذخیره می‌شوند؛ پس از رفرش، گفتگوی فعال بازیابی می‌شود.
7. **آرشیو** → `/archive` فهرست گفتگوها با جستجو، ادامه، حذف تکی و پاک‌سازی کامل.

| کنترل | وضعیت | محل پیاده‌سازی |

| اعتبارسنجی ورودی | ✅ | بررسی نوع و غیرخالی بودن `message` |

## ۷. استقرار

| مورد | مقدار |
|---|---|
| فایل Compose کانونی | `docker-compose.dev.windows.yml` |
| نام کانتینر | `nurse-prototype-dev` |
| پورت | `127.0.0.1:3000` |
| دستور بالا آوردن | `docker compose -f docker-compose.dev.windows.yml up -d --build` |
| Healthcheck | `http://127.0.0.1:3000/api/health` |
| لاگ‌ها | `docker logs nurse-prototype-dev` |

**چرا فایل Compose جداست:** bind-mount مستقیم از ویندوز به لینوکس (`.:/app`) روی فایل‌های زیاد کند است؛ این فایل از named volume برای کل کد استفاده می‌کند و فقط پوشه‌های کاری را زنده نگه می‌دارد.
