# PROJECT-RULES — قوانین پروژه (AI-Driven)

> این سند «قانون» است. هر ایجنت، هر انسان و هر PR باید با این قوانین سازگار باشد. نقض = رد کار.
> نسخه: ۱.۰ · تاریخ: ۱۴۰۵/۰۷/۰۸

---

## قانون ۰ — اصل حاکم

> **نمونه، هرگز به‌جای واقعیت جا زده نمی‌شود.**
> هر جا داده واقعی نداریم، صریح بگو «نمونه». پنهان‌کردنِ نمونه، خطای اخلاقی است نه صرفاً فنی.

دلیل: سند T10 — پاسخ حقوقیِ نادرست می‌تواند به پرستار آسیب شغلی بزند، و اعتماد از دست‌رفتنی‌ترین دارایی است (T01 بند ۷).

## قانون ۱ — قیدهای سخت (Hard Constraints)

این‌ها **قابل مذاکره نیستند**. هر کاری که یکی را نقض کند، در همان لحظه رد می‌شود.

| # | قید | منبع |
|---|---|---|
| H1 | هیچ خروجی‌ای نباید عبارت «حق با توست»، «قطعاً تخلف شده»، «تضمین نتیجه» داشته باشد | T10 نقطه‌کور ۲ · T05 بند ۳ |
| H2 | هر پاسخ در نسخهٔ نمونه باید برچسب «نمایشی/نمونه» داشته باشد | SCOPE §۱ |
| H3 | سه سطح قطعیت الزامی است: **قطعی · احتمالی · نیازمند بررسی** | T10 · T05 |
| H4 | استناد باید «نزدیک به ادعا» باشد؛ بدون استناد = باید صریح بگوید «مبنای کافی نیست» | T05 بند ۴ |
| H5 | هرگز نتیجهٔ یک پروندهٔ دیگر به‌عنوان «تضمین موفقیت» نمایش داده نشود | T05 بند ۶ |
| H6 | هیچ دارک‌پترن: FOMO، تایمر فشار، آمار ساختگی، تهدید | T07 بخش ۴ · T03 (لحن آرامش‌بخش) |
| H7 | در UI، پاسخ قطعی بدون دادهٔ کافی **قفل فنی** دارد (نمایش `عدم‌اطمینان`) | T10 · T08 (آستانهٔ اطمینان) |
| H8 | هیچ دادهٔ شخصی واقعی وارد نسخهٔ نمونه نمی‌شود | T09 · T10 نقطه‌کور ۳ |

## قانون ۲ — استاندارد پاسخ (قالب اجباری)

هر پاسخ ایجنت باید دقیقاً این ۴ بخش را داشته باشد — بدون حذف و بدون اضافه‌کردن بخش پنجم:

```
[سطح قطعیت: قطعی | احتمالی | نیازمند بررسی]

۱. آنچه از مسئله فهمیدم
۲. آنچه هنوز باید مشخص شود
۳. مبنای قابل‌بررسی
۴. قدم‌های ممکن (با میزان قطعیت هرکدام)
```

**نمونهٔ درست (سطح: نیازمند بررسی):**
```
🔶 نمایشی — پاسخ نمونه است

۱. فهمیدم: فیش شما کمتر از حد انتظار پرداخت شده.
۲. هنوز لازم است: سابقهٔ شیفت‌های همان ماه.
۳. مبنا: در این نسخه دادهٔ واقعی متصل نیست (نمونه).
۴. قدم‌ها: گرفتن ریز شیفت‌ها ← مقایسه با فیش ← درخواست توضیح
```

## قانون ۳ — زبان و لحن

| قاعده | مثال درست | مثال غلط |
|---|---|---|
| خروجی «چه کار کنم» | «مدیریتت حق ندارد این را کم کند؛ این متن را بفرست» | «طبق بند ۳ قانون کار…» |
| غیرترساننده | «این مورد نیاز به بررسی بیشتر دارد» | «کارفرمایت تخلف کرده» |
| آرامش بدون اطمینان کاذب | «نمی‌توانم قطعی بگویم؛ اما می‌توانم قدم بعدی را بگویم» | «نگران نباش، حتماً حق توست» |
| پاراگراف | حداکثر ۳ خط | پاراگراف ۸ خطی |

## قانون ۴ — تگ‌کردن کار

هر PR/فایل باید در انتهای خود داشته باشد:

```
Trace: T06 (طراحی رابط) · T05 (قالب پاسخ)
Rule: H3,H6
Owner: agent-ui-02
Status: draft|review|approved
```

بدون این چهار خط، کار «بدون مالک» تلقی و رد می‌شود.

## قانون ۵ — تعریف «تمام‌شده» (Definition of Done)

کاری تمام است که **همهٔ** این‌ها را داشته باشد:
- [ ] در `ui/` قابل اجرا یا قابل مشاهده باشد
- [ ] روی گوشی (۳۶۰px) و دسکتاپ درست دیده شود
- [ ] حالت روشن و تاریک هر دو کار کند
- [ ] هیچ‌کدام از H1 تا H8 نقض نشده باشد
- [ ] تگ‌های قانون ۴ موجود باشد
- [ ] در `ui/CHECKLIST.md` تیک خورده باشد

---

## قانون ۶ — اگر مطمئن نبودی

1. **حدس نزن.** بنویس: `TODO: نیازمند تصمیم D<n>` و همان‌جا متوقف شو.
2. **دو گزینه بده، نه یکی.** `گزینه الف (پیشنهادی) / گزینه ب` — انتخاب با PO است.
3. **عدد نسازد.** اگر آمار یا مبلغ لازم است و نداری → `نمونه` بنویس یا حذف کن. (قانون ۰)
4. **خارج از دامنه نرو.** اگر فکر می‌کنی قابلیت لازم است → در `BACKLOG.md` بنویس، در کد ننویس.

## قانون ۷ — مالکیت و مرزها

- هر ایجنت فقط در `docs/` خودش می‌نویسد؛ هیچ‌کس `docs/` دیگری را ویرایش نمی‌کند.
- `ui/` مالک مشترک است: هر ایجنت فقط فایل/بخش خودش را می‌سازد.
- هیچ ایجنتی حق ندارد خودش تصمیم محصولی بگیرد → فقط پیشنهاد می‌دهد.
